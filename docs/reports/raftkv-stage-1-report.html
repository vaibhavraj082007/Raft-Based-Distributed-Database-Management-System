Stage 1 delivers the deterministic substrate that all later distributed-systems behavior will run on. It is intentionally not a Raft implementation yet.

What was built

A single-threaded discrete-event simulator now owns every source of non-determinism in the system. Simulated time is a logical millisecond counter that advances only when an event is dispatched. A single frozen SplitMix64 PRNG supplies all randomness. A fake network delivers typed messages with latency, drops, directed link blocks, and partitions. A per-node asynchronous fake disk models visible and durable bytes separately, so only an explicit Sync survives a crash. Nodes are actors constructed by factories; a crash discards the node instance, increments an epoch, and guarantees that old messages, timers, and I/O completions can never leak into the restarted node.

Around that core, the stage adds canonical text traces, FNV-1a trace and state hashes, rich invariant failures with seed and replay commands, a panic boundary, a 5-node ping/journal workload with a deterministic chaos driver, a simctl command, a checked-in golden trace, 41 tests, and an AST-based guard against non-deterministic APIs.

What is deliberately not built

There is no Raft leader election, log replication, WAL, LSM-tree, key-value API, sharding, transaction layer, SQL, or dashboard. No Stage 2 code exists. The fake disk is a device model, not the production storage engine. The simulator is a correctness harness, not a throughput benchmark.

Key outcome. The same seed now reproduces byte-identical trace bytes, trace hash, and state hash across fresh simulator instances, interleaved instances, and separate OS processes. A failing seed reports the exact replay command. This is the property every later bug hunt depends on.

01   Context

Project vision and architecture

The goal is a 5-node replicated key-value database built from first principles: Raft, a write-ahead log, an LSM-tree, a linearizable KV API, and later sharding, transactions, SQL, and a dashboard. The unusual part is not the database; it is the testing method.

Why deterministic simulation

Distributed systems fail in rare interleavings: a message arrives after a restart, a leader crashes between a disk write and an RPC reply, a partition heals while a vote is in flight. Reproducing those schedules with real clocks, real sockets, and OS scheduling is unreliable. The project follows the FoundationDB and TigerBeetle approach: put the whole cluster in one process, replace the outside world with deterministic fakes, drive them from one seeded PRNG, and make every run replayable.

The simulator is therefore a first-class deliverable, not test scaffolding. It owns time, scheduling, messages, disk durability, node lifecycle, randomness, tracing, and invariant checks. Later layers never reach around it.

Rules that govern every layer

Determinism

  • One seeded PRNG per simulation, consumed in event order.
  • Logical Tick milliseconds; no wall clock.
  • Stable event ordering by (tick, sequence).
  • No goroutines, channels, real timers, real sockets, or global RNG.
  • No map iteration where order affects behavior or output.

Correctness

  • Invariants run after every simulation step.
  • Persist term, vote, and log before replying (later stage).
  • Crash discards volatile state; only durable bytes survive.
  • Failures report seed, version, step, event, and replay command.
  • Later stages may import internal/sim; never the reverse.

Invariants reserved for later stages

The Stage 1 framework is generic and stateful. When Raft and the KV layer arrive, the same hook will check: only one leader per term; no two nodes disagree about a committed log entry; committed entries never disappear; and a bank workload with 100 accounts × 1,000 always sums to 100,000. Those checks are not implemented yet because the objects they inspect do not exist yet.

Stage boundary. Stage 1 ends at a tested simulator and a toy workload. It does not claim Raft correctness, linearizability, or durable production storage. Moving on requires explicit approval.

03   Architecture

Simulator architecture

Stage 1 behaves like a tiny operating system for one process. It owns the clock, the run queue, every byte of simulated I/O, every random draw, and the lifecycle of every node. Application code is a set of passive actors that can only act through the capability surface the simulator hands them.

Package boundaries

Dependencies point in one direction: cmd/simctl depends on internal/scenarios, which depends on internal/sim. internal/sim has no project-internal dependencies and imports only the Go standard library. Later layers will be allowed to import internal/sim; internal/sim will never import them. This preserves the simulator as an external correctness harness rather than a framework that can be bent to hide a bug.

ComponentResponsibilityDeterminism mechanism
ClockAdvance simulated time only by dispatching the next event.Logical Tick; no wall clock.
Event queueOrder all boots, timers, sends, deliveries, I/O completions, chaos actions, and the finalizer.Stable min-heap on (at, seq).
RandomnessSupply every random choice: peer selection, timer jitter, network latency, drops, and chaos.One frozen SplitMix64 stream per simulation.
NetworkDeliver typed messages with latency jitter, packet loss, partitions, and epoch safety.Draws from the one RNG in send order; delivery is another event.
DiskModel asynchronous per-node files with visible and durable bytes.FIFO issue order; completion events; epoch-filtered after a crash.
LifecycleBoot, crash, and restart nodes; discard volatile node state; preserve only durable disk state.Fresh factory instance and monotonically increasing boot epoch.
TraceRecord every behavior-relevant decision and produce a replay artifact.Explicit ASCII fields; no maps, pointers, floats, or timestamps from the OS.
InvariantsCheck structural and scenario properties after every event and at the end.Registration order; checks are pure and cannot draw randomness.
FailureTurn a violation or panic into a deterministic report with a replay command.Seed, scenario, version, step, tick, event, cause, trace tail.

The execution loop

1 · ScheduleAssign the next sequence number and insert an event by (at, seq).
2 · PopTake the earliest event; set Now() to its tick; increment the step counter.
3 · TraceWrite the event record before the handler runs.
4 · DispatchInvoke scenario logic or node callback. New work becomes new events.
5 · CheckRun structural checks and every invariant, then update hashes and continue.

There is no scheduler race and no hidden concurrency. A node can only send a message, schedule a timer, issue disk I/O, or draw randomness through Env. It cannot reach the simulator, another node, the host clock, or the real filesystem. The simulator owns the network and disk and can therefore re-check conditions at both send time and delivery time.

Architectural rule. Any behavior that can affect the trace, the final state, or a failure must be an event. Test setup is the only exception, and it happens before the run starts.
04   Components

Component deep dives

Each subsystem below is deliberately small. The goal is not to model every detail of a real operating system; it is to preserve the failure modes that a Raft implementation must survive, while making each one replayable.

4.1 Logical clock and event queue

Simulated time is type Tick int64, measured in simulated milliseconds. It jumps directly to the next event; it never advances while the queue is idle. Every event has an absolute tick and a monotonically increasing sequence number. Same-tick events therefore execute in scheduling order, and an event scheduled during another dispatch at the same tick runs later, never immediately.

Entry pointSemantics
RunUntil(t)Dispatch every event with at <= t; if the queue empties first, advance the clock to t.
RunSteps(n)Dispatch at most n events, then run the final invariant check.
RunUntilIdle()Drain the queue completely, then run the final invariant check.
ScheduleFunc(at, name, fn)Scenario-controlled event insertion. Past scheduling is rejected.
After(delay, tag)Node timer insertion. Timer cancellation is supported; stale timers are ignored.

Default guards are one million steps and one billion ticks. A run that reaches either limit fails with a replayable Failure instead of hanging. An event scheduled in the past is rejected; a queue that somehow contains one is caught by the structural invariant check.

4.2 Randomness

The simulator uses a frozen in-repo SplitMix64 generator rather than math/rand. This removes any dependency on a Go release's internal algorithm or seeding behavior. There is exactly one generator per Sim, and every draw is made during event dispatch in queue order. 

func (r *Rand) Uint64() uint64 {
    r.state += 0x9e3779b97f4a7c15
    z := r.state
    z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9
    z = (z ^ (z >> 27)) * 0x94d049bb133111eb
    return z ^ (z >> 31)
}

Integer ranges are inclusive and use unbiased rejection sampling. A Chance(0) or Chance(1000) returns without consuming a draw, which is itself a stable rule. Golden-vector tests pin the first outputs for known seeds, so an accidental algorithm change is caught immediately.

4.3 Fake network

Send is asynchronous and returns immediately. The network records the send, clones the payload, samples an inclusive latency in [min, max], and schedules a delivery event tagged with the destination's current boot epoch. Delivery re-checks liveness, epoch, and partition state, so a partition forming while a message is in flight is still enforced.

t=11  send from=4 to=2 kind=ping bytes=8
t=11  drop from=4 to=2 kind=ping reason=partition
t=31  send from=2 to=5 kind=pong bytes=8
t=33  recv from=2 to=5 kind=pong bytes=8
Drop pointReasonWhat it proves
Sendunknown-nodeActor code cannot address an unregistered peer.
SenddownA crashed receiver does not accept new messages.
Send / deliverypartitionDirected blocks are enforced even for messages already in flight.
SendlossThe configured per-mille drop rate is sampled from the one RNG.
Deliverystale-epochA message from before a restart can never enter the new incarnation.

Partitions are a set of directed blocked links. Block and Unblock manipulate one direction; Partition blocks every cross-group direction; Isolate blocks every link touching a node; HealAll clears the set. Defaults are 1–4 ticks of latency and no loss.

4.4 Fake crash-safe disk

Each node owns one asynchronous disk device. Operations are processed serially in issue order, with a configurable latency. Every file has two byte views: visible bytes that reads see, including completed but unsynced writes, and durable bytes that survive a crash. A completed Sync copies every file's visible bytes into its durable bytes.

The visible view makes read-your-writes work before a sync. A crash cancels all pending operations, discards old completion events by epoch, and reverts every visible file to its durable bytes. Restart constructs a new node over the same durable disk. A sync atomically persists every preceding append in every file; there are no torn writes or bit rot in Stage 1.

OperationVisible effectDurable effect
ReadReturns bytes from the visible file, truncated at EOF; missing file yields empty bytes.None.
AppendAppends atomically to the visible file.None until a later Sync completes.
ReplaceReplaces the visible file atomically.None until a later Sync completes.
SyncNo data change.Copies every visible file to durable storage.
ListReturns sorted name<TAB>size lines of visible files.None.

4.5 Node lifecycle and epochs

A node is not a persistent Go object. It is an incarnation produced by a factory. The simulator calls factory(env) on boot, stores the resulting actor, and then calls Start(). On crash, the actor and its environment are discarded, the epoch increments, timers are removed, and the disk reverts to durable data. Restart calls the factory again.

BootFactory creates a fresh actor with a new Env.
RunCallbacks mutate only actor state and issue events.
CrashEpoch++, actor nil, timers canceled, disk reverted.
StaleOld messages, timers, and I/O completions are filtered.
RestartFactory runs again; only durable disk survives.
ArtifactCarries epoch?After restart
Network deliveryYes, destination epoch at send timeDropped with stale-epoch.
TimerYes, owner epochCanceled on crash; any stale delivery is ignored.
Disk completionYes, issuing epochDropped as stale; pending operations were canceled.
Node memoryNo, intentionally notGone. A fresh factory instance starts from durable bytes.

Panics inside a node callback or boot are caught at the dispatch boundary and converted into a deterministic Failure containing the panic text, a Go stack trace, and the usual replay information. A panic is therefore a finding, not a crashed test process.

4.6 Canonical trace, hashes, and replay

The trace is canonical UTF-8 text, one event per line, with explicit fields. Nothing is printed with Go's default map or pointer formatting. The first line names the simulation version, seed, scenario, and trace level. Each record carries the simulated tick and step count, followed by a type-specific payload. 

sim v=1 seed=42 scenario=ping level=0
t=0 step=0 nodes=1,2,3,4,5
t=0 step=1 event seq=1 kind=boot desc=node=1
t=0 step=1 boot node=1 epoch=0
t=0 step=6 event seq=6 kind=scenario desc=chaos
t=0 step=6 partition groups=1,2|3,4,5
t=11 step=12 send from=4 to=2 kind=ping bytes=8
t=11 step=12 drop from=4 to=2 kind=ping reason=partition

The rolling trace hash is FNV-1a 64 over the exact bytes written. The state hash is a separate canonical digest over the simulation version, seed, scenario, clock, step, event and timer sequence counters, RNG state, node order and liveness, epochs, node snapshots, sorted timers, sorted blocked links, sorted disk files with visible and durable bytes, the queued events, and the statistics counters. Both are printed by the CLI and compared by tests.

Trace levels

  • events — behavior records: boot, send, receive, drop, partition, disk completion, chaos, crash, restart.
  • decisions — adds every RNG draw with its label and value, for deep debugging.

The golden trace is checked in at level events. The hash covers whatever level is enabled.

Failure artifact

  • Seed, scenario, simulation version.
  • Step, tick, and triggering event.
  • Failed invariant and cause.
  • Last 40 trace lines.
  • Exact replay command.

Panics add a Go stack trace inside the cause.

4.7 Invariants

Invariants run after every dispatched event and once after each run API returns. They receive the simulator but may not mutate it, draw randomness, or schedule events. A panic inside an invariant becomes a normal failure. The structural checks are always enabled: no negative time, no event in the past, and a valid queue.

InvariantStageStatus
Non-decreasing time and no past events1active
Ping recovery ≤ cumulatively synced records per node1active
One leader per term2later
No committed-log disagreement across nodes2–3later
Committed entries never disappear3later
Bank total always 100,0004later

The Stage 1 recovery invariant is stateful: it remembers, per node, how many sync completions have been observed in every incarnation. A restart may recover at most that cumulative count. This is the invariant that exposed bug S1-001.

05   Reproducibility

Determinism and replay

Determinism is a property of the whole run, not a feature of the RNG. It requires a single source for time, scheduling, randomness, I/O, lifecycle, and output encoding. Stage 1 tests each link in that chain and then tests the chain end-to-end.

The contract

A run is reproducible when the simulation version, binary, seed, scenario, and configuration are identical, all random draws come from the single simulator RNG in event order, all ordering is by (tick, sequence) or an explicitly sorted key, and all output is canonical. The trace records the version because exact replay is defined per version: a semantic change that alters draw order or event ordering requires a version bump and the original commit for cross-version reproduction.

SeedOne uint64 initializes the frozen SplitMix64 stream.
Event orderOne heap orders all work by (tick, seq).
No ambient inputNo wall clock, OS scheduling, env, filesystem, or sockets.
Canonical outputExplicit fields, sorted keys, no maps or pointers.
ArtifactTrace bytes, trace hash, state hash, and replay command.

Four levels of evidence

LevelTestWhat it rules out
Fresh in-process runsTestSameSeedProducesIdenticalTraceHidden state left over between runs; nondeterministic RNG or event order.
Interleaved simulatorsTestInterleavedSimsDoNotShareStateGlobal mutable state, shared RNG, package-level counters.
Separate OS processesTestCLIReplayAcrossProcessesProcess-local memory layout or run-order dependence.

Seed sweepTest100SeedSmokeA single lucky seed; invariant violations across many chaos schedules.

What the hashes cover

Trace hash

FNV-1a 64 over the exact trace bytes. It detects any change in the sequence of recorded events, fields, or formatting. Tests compare both the byte buffer and the hash, so a hash collision cannot hide a difference.

State hash

A canonical digest of the simulator and node state, not just the trace. It covers liveness, epochs, RNG state, timers, partitions, disk contents, the pending queue, and statistics. It detects state divergence even if the visible trace happens to look identical.

The default trace level records behavior, not every RNG value. That keeps the golden file readable. -decisions adds each draw, which is useful when investigating why two plausible executions diverged.

Replay in practice

A failure report is self-contained enough to hand to another engineer: 

simulation failed: seed=77 scenario=invariant-test version=1 step=1 tick=0 \
  event=seq=1 kind=scenario desc=one
invariant=always-fails
cause: boom
replay: go run ./cmd/simctl -seed 77 -scenario invariant-test -ticks 0 -trace

The CLI validates a negative seed before conversion, so there is one canonical decimal representation per seed. A replay command always includes the scenario and tick limit. The same seed on the same version and binary must reproduce the same failure at the same step and tick.

Known boundary. Determinism does not survive an intentional semantic change or a different binary. If a change alters draw order or event order, bump Version, update the golden trace, and document it. The report, README, and trace header all carry the version for this reason.

Statistics

Every simulation maintains counters for events, messages sent/delivered/dropped, disk operations, boots, crashes, and restarts. The CLI prints them after the run. They are useful for quickly spotting an overly destructive chaos schedule, but they are not a correctness signal; invariants are. 

run v=1 seed=42 scenario=ping nodes=5 end-tick=500 status=ok
steps=504 events=504 sent=176 delivered=80 dropped=96 disk-ops=277 \
  boots=7 crashes=2 restarts=2
trace-hash=25895005889e1714 state-hash=c38a6906689885f9

Failure report shape

When an invariant fails, a panic escapes a callback, a trace write fails, or a guard trips, the simulator freezes and returns a *Failure. The report is deterministic; it contains no wall-clock timestamp and no pointer addresses.

seed · scenario · version · step · tick

event — sequence, kind, description of the triggering event

invariant — name, or empty for a dispatch/panic failure

cause — the underlying error or panic with stack trace

replay — exact go run ./cmd/simctl … command

last trace — the 40 most recent records

Invariant discipline

  • Checks run in registration order and must be pure with respect to simulation state.
  • Checks may keep their own history, but must not draw randomness or schedule work.
  • A panic inside a check becomes a normal failure with the invariant name.
  • Structural checks are always on, even when a scenario registers no invariants.
  • Every run performs one final check after the last event, so an empty tail is still checked.
Design consequence. The invariant hook is the place where Raft and KV correctness will live. Stage 1 proves the hook is called at the right times, can be stateful, and produces an actionable replay artifact.
07   Workload

Stage 1 workload and CLI

The ping scenario is intentionally not a Raft placeholder. It is a small but complete journaling workload that exercises every Stage 1 subsystem: timers, randomness, messaging, partitions, asynchronous disk I/O, sync durability, crashes, fresh restarts, recovery, and a stateful invariant.

PingNode behavior

BootIssue a journal read and schedule the first ping after 10–20 ticks.
PingPick a peer, increment the sequence, send 8-byte big-endian payload, journal and sync.
ReplyOn ping, count receipt and send a cloned pong to the sender.
ObserveOn pong, increment the inbound-pong counter.
RecoverOn the journal read, count newline-terminated records and mark recovery complete.

Each outgoing ping writes one line, p <node> <seq>\n, then issues a Sync. The node increments its durable-record count only when the sync completion arrives. This deliberately models the Raft rule that a node must not treat data as durable until the persistence acknowledgement is delivered. The journal is append-only in Stage 1; a future WAL will add truncation, checksums, and torn-write tests.

t=0  boot node=4  →  disk.read journal
t=11  timer node=4  →  peer=2  →  send ping bytes=8
t=11  disk.append + disk.sync journal
t=11  drop ping reason=partition
t=13  disk sync complete → durable++
t=24  timer node=4  →  next ping

On restart, a fresh PingNode is constructed. Its in-memory counters start at zero, its incarnation increments, and it reads the journal left by all prior incarnations. The recovery invariant compares the recovered line count with the cumulative sync completions the simulator actually observed. A node must never come back with more records than could possibly have been synced.

Chaos driver

Chaos actions are scheduled simulator events, not a separate goroutine. The first action fires at tick 0 and then recurs after 50–150 ticks, consuming the same RNG stream as node and network behavior. This is important: changing the chaos schedule changes the execution exactly as visibly as changing a node's timer.

ActionWeightEffect
Crash a live node25%Epoch++, discard memory, cancel timers and I/O, revert visible disk.
Restart a down node20%Call the factory for a fresh incarnation; recover durable journal.
Partition the cluster20%Choose a cut point and block all cross-group directed links.
Heal all links10%Clear the blocked-link set.
Change drop rate15%Choose a new uniform per-mille loss rate in 0–300.
Change latency10%Choose a new inclusive range from 1–3 up to 1–7 ticks.
Finalize at endonceHeal, zero loss, set latency 1–2, and restart every down node.

The finalizer does not require liveness at every intermediate point. It makes the end-of-run summary meaningful and ensures a restarted node has a chance to finish recovery before the run stops.

Key evidence in detail

Byte-identical replay

Three fresh simulators with seed 42 produce the same trace bytes, trace hash, and state hash. Two independent simulators advanced alternately with RunSteps(1) produce exactly the same trace as either one run alone. A built CLI invoked twice in separate processes produces identical bytes.

Crash and durability

Unsynced appends are visible to reads, then disappear after a crash. Synced bytes survive. Pending operations never deliver a completion across the crash. A sync persists all preceding appends. The restarted node is a new object, and stale timers, messages, and I/O completions are filtered.

Chaos and invariants

The 100-seed smoke test runs five nodes with random crashes, restarts, partitions, loss changes, and latency changes for 300 ticks. The recovery invariant holds for every seed, including the multi-restart scenario that exposed S1-001.

Static guard and vet

The AST guard rejects go, select, channels, channel operations, time.Now/Sleep/After/Tick and timer constructors, math/rand, crypto/rand, net, and filesystem/system access in simulated code. Vet and race detection add the compiler's own checks.

Performance envelope

The 100-seed smoke run completes in roughly 0.06 seconds on the verification machine, far below the 10-second Stage 1 budget. This is not a throughput benchmark; the number exists to catch accidental super-linear behavior in scenario setup or invariant checks. The simulator deliberately avoids optimization that would complicate determinism.

What is not proven by Stage 1

The suite proves the simulator's own behavior and the ping workload's recovery accounting. It does not prove Raft safety, log matching, linearizability, or durable production storage, because those objects do not exist yet. Stage 2 will add its own tests and invariants rather than extending these results by assumption.

10   Bug log

Bug found and fixed — S1-001

One real bug was found during Stage 1 verification. It was a flaw in the test invariant's accounting, not in the simulator's disk model: the invariant compared a cumulative recovery count against a per-incarnation maximum, so it would falsely fail after the second restart.

FieldDetail
IDS1-001
Stage / scenarioStage 1, forced-restart ping invariant test (seed 5)
SymptomAfter two or more restarts, the recovery invariant claimed a node had recovered more records than it had ever synced, even though the journal was legitimate.
Root causeThe checker remembered the maximum durable count seen in any single incarnation. Recovery is cumulative across incarnations, so the second restart could recover more than the per-incarnation maximum while still being fully valid.
FixTrack cumulative sync completions across all incarnations, keyed by an incarnation counter; compare recovery against that cumulative sum.
Regression testTestPingInvariantAcrossMultipleRestarts — three forced crash/restart cycles, 500 ticks, asserts incarnation 4 and non-zero recovery.
Statusfixed and covered

Why the bug mattered

The simulator was behaving correctly: durable bytes survived, the new incarnation recovered them, and the journal grew across restarts. The invariant was under-counting legitimate durability. Left in place, it would have produced false failures and eroded trust in the test suite once later stages added more restarts. The fix keeps the invariant strict but makes its ledger match the journal's actual lifetime.

Before

maxDurable[node] = the largest durable count observed in one incarnation. On restart, recovery was compared with that maximum.

Incarnation 1 syncs 10; incarnation 2 syncs 8; restart recovers 18. 18 > 10, so the checker falsely fails.

After

cumulativeSynced[node] = sum of every sync completion observed across incarnations. On restart, recovery is compared with the cumulative sum.

Incarnation 1 syncs 10; incarnation 2 syncs 8; restart recovers 18. 18 ≤ 18, so the checker passes.

Reproduction and location

go test ./internal/scenarios -run TestPingInvariantAcrossMultipleRestarts -v

# The test schedules crash/restart at ticks 50/51, 150/151, and 250/251,
# then runs to tick 500. Node 1 ends at incarnation 4.

The bug and its regression test are recorded in the README bug log as required by the project process. No other bugs are logged for Stage 1.

11   Boundary

Limitations and next stage

Stage 1 is complete, but it is deliberately incomplete as a database. The boundary is explicit: there is a tested deterministic substrate and a toy workload, and nothing that claims Raft safety or production storage.

Limitations of this stage

AreaStage 1 boundary
RaftNo terms, elections, votes, AppendEntries, commit rule, snapshots, or membership changes.
Storage engineThe disk is a fake raw device. There is no WAL, LSM-tree, checksum, truncation, compaction, or recovery format.
Key-value layerNo commands, client IDs, deduplication, linearizability checker, or state machine.
Distributed invariantsThe framework is ready, but leader uniqueness, committed-log agreement, commit durability, and bank totals arrive with the layers they inspect.
Network realismLatency and drops are modeled; duplication, corruption, and explicit reordering knobs are not.
Disk realismNo torn writes, bit rot, fsync failure, or partial crash; completed writes are atomic.
Lifecycle realismRestart is immediate; there is no boot delay, crash recovery period, or process-level resource failure.
WorkloadOne toy scenario, one RNG stream, and a 100-seed smoke sweep — not an exhaustive state-space proof.
PerformanceNo throughput, latency, or memory benchmarking. Determinism and clarity take priority.
Static guardThe AST scan is a strong tripwire, not a formal proof; reflection or indirect calls could evade it.

What Stage 2 must add

  1. Raft actor state — current term, voted-for, role, commit index, and a log with term/index entries.
  2. Persistence before reply — term, vote, and log writes must complete their sync before an RPC that depends on them is answered. The Stage 1 disk already supports this shape.
  3. Election and heartbeats — randomized election timeouts through the simulator RNG, request-vote handling, and leader heartbeats as timer events.
  4. Replication — AppendEntries, next/match indices, conflict truncation, and commit advancement under the Figure 2 rules.
  5. Raft invariants — one leader per term, no committed-log disagreement, and committed entries never disappear. These become per-step checks.
  6. Tests — partition, crash, restart, delayed delivery, lost messages, stale terms, and replay of every discovered seed. No later layer advances without them.
Stop point. Stage 2 has not started. No Raft, storage, KV, sharding, SQL, or dashboard code exists in the repository. Beginning the next stage requires explicit approval.
